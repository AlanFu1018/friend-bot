## 🔴 P0-1：Burst 場景把使用者畫像改成別人的名字（資料污染）✅ 已修復

**位置**：`src/friend_bot/bot/client.py:192-193`

```python
for uid in all_user_ids:
    asyncio.create_task(self.memory_extractor.process_unextracted_for_user(uid, latest_user_name))
```

迴圈跑過本批**每一個** `uid`，但第二個參數固定傳 `latest_user_name`——**最後一則訊息發言者**的名字。錯誤的名字一路流進提煉 prompt（`build_multi_entity_extraction_prompt` 的「名稱: {speaker_name} (ID: {speaker_id})」），模型照著回傳，`_safe_apply_updates` 便把它寫回畫像。

### 實測結果

模擬「岡部先講、桶子最後講」的 Burst：

```
提煉前：  ID 1001 = 岡部          ID 2002 = 桶子
          → prompt 告訴模型：發言者是 '桶子' (ID: 1001)   ← 錯誤名字進入 prompt
提煉後：  ID 1001 = 桶子   ←汙染   ID 2002 = 桶子
get_known_users_map() → {'桶子': '2002'}                  ← 岡部從索引中消失
```

事實內容仍是岡部的（`自稱狂氣科學家`），但**標籤錯了**。

### 連鎖後果

1. `get_known_users_map()` 從兩筆塌縮成一筆，維度 B 名稱掃描再也認不出岡部。
2. **系統自己製造了 P1-2 的暱稱碰撞**，不必等兩人碰巧同名。
3. `/kurisu-profile` 會把岡部的畫像顯示成桶子。
4. Prompt 的【其他群友畫像】可能出現兩個都叫「桶子」的人。
5. **每一次 Burst 都在累積污染**。

### 觸發條件

Burst（≥2 位發言者）＋ 非最後發言者有未提煉訊息 ＋ 模型回傳任何實質變更（`interaction_notes` 幾乎必定有）。單人對話不受影響。

> 註：`_safe_apply_updates` 的 `has_changes` 判斷**不包含 `user_name`**，因此純改名不會觸發寫入；但只要有任何其他變更，錯誤的名字就會被一併帶著寫進去。

### 資料修復

`messages` 表保存了每則訊息當下的正確 `user_name`，可取每位 `user_id` 最新一筆回填 `user_profiles.user_name`。

## 🔴 P0-3：每則訊息都被提煉兩次（好感度雙倍、熱度灌水、API 成本雙倍）✅ 已修復

**位置**：`client.py:192-193`（JIT）與 `client.py:383-390`（收尾提煉）

同一批訊息會被兩條路徑各處理一次——**不分 Burst，每則單人訊息也會**。

### 實測結果

```
初始好感度 30
[JIT 之後]      好感度=32   facts=[('喜歡喝 Dr Pepper', hits=1)]
[收尾提煉之後]  好感度=34   facts=[('喜歡喝 Dr Pepper', hits=4)]
同一則訊息共觸發 2 次 Gemini 提煉呼叫
```

| 影響 | 實際值 |
| :--- | :--- |
| 好感度 delta | 模型給 +2 → **實際 +4** |
| 事實熱度 | 應為 `hits=1` → **實際 `hits=4`**（第二次被 `merge_facts` 誤判為「重複確認」+3）|
| Gemini 提煉呼叫 | 每則訊息 **2 次** |

**第三項最陰險**：每則訊息都在灌水軌道 1（熱度）。`hits` 本應反映「使用者反覆展現的核心人設」，實際上反映的是「這條事實被提煉過幾次」，而每次都算兩次 → **三軌檢索的熱度排序整個失真**。

### 根因（兩個疊加）

1. `get_unextracted_messages_by_user` **沒有頻道過濾**。`client.py:192` 的註解寫「消化在場用戶在**監聽頻道**累積的訊息」，但 SQL 只篩 `extracted=0 AND is_bot=0 AND user_id=?`，連當前對話頻道剛存入的訊息也一起撈走。
2. 收尾提煉 `extract_and_update` **既不檢查也不設定 `extracted` 旗標**，所以它處理過的訊息下次還會被 JIT 再撈一次。

## 🟠 P1-1：`merge_facts` 無法辨識否定／更正語意（錯誤事實自我強化）✅ 已修復

**位置**：`src/friend_bot/memory/memory_manager.py:176` 附近（`merge_facts`）

新舊事實是否「相同」只靠雙向子字串比對：

```python
f["text"].lower() == new_f_lower
or new_f_lower in f["text"].lower()
or f["text"].lower() in new_f_lower
```

若新事實是舊事實的**否定句**，字面上會完整包含舊事實，於是被誤判為「重複確認」。

### 實測結果

```
舊事實「喜歡台北」(hits=1) + 新事實「已經不喜歡台北了」
→ 合併後：[('喜歡台北', 4)]
```

**新的更正事實完全消失，舊的錯誤事實熱度反而從 1 漲到 4。**

`hits=4` 使它更容易被三軌檢索的軌道 1（熱度）選中 → 更常被講出來 → 使用者再次否認 → 再次被誤判為重複確認、熱度再漲。這是一個**正回饋迴路**，錯誤事實會越錯越響亮。

### 修復內容

新增否定極性判斷，在字面配對成功後再比對兩條事實的極性：極性相同才算重複確認並加權，極性相反則視為矛盾，**以新事實就地取代舊事實**（熱度歸 1，不加權）。

| 新增方法 | 職責 |
| :--- | :--- |
| `has_negation(text)` | 判斷是否帶否定語意 |
| `topic_key(text)` | 取出「去掉否定詞後的主題」，供同主題配對 |
| `_is_same_topic(a, b)` | 主題配對，含短字串防誤配保護 |

**為什麼需要 `topic_key`**：極性比對必須先配對到同一主題才有意義。只用原文比對時，加上「不」的方向能命中（「喜歡台北」是「已經不喜歡台北了」的子字串），但**拿掉**「不」的方向會斷開子字串關係——「不喜歡吃辣」與「現在喜歡吃辣了」互不包含，兩條矛盾事實會被當成不相干而同時保留。剝除否定詞後兩者主題同為「喜歡吃辣」，才配得起來。

**刻意保守的判斷邊界**：只採用「不 / 沒」與一組英文否定詞；「不錯 / 不過 / 差不多」等含「不」卻非否定的詞會先被保護；**不採用「未 / 無 / 非」**，因為「未來」「無聊」「非常」會造成大量誤判——「非常喜歡台北」若被判為否定，就會把「喜歡台北」誤刪。

判斷偏誤方向是刻意的：**漏判只會退回原本的重複確認行為，誤判卻會刪掉一條仍然成立的事實。**

### 仍未涵蓋

字面主題不同的語意矛盾無法辨識，例如「沒有養寵物」與「養了一隻貓」會同時保留。這需要語意理解，屬於 P3 的範圍。

## 🟠 P1-2：暱稱同名碰撞 ✅ 已修復

**位置**：`memory_manager.py` 的 `get_known_users_map`

原本回傳純粹的 `{暱稱小寫: user_id}` 字典，同名時後者覆蓋前者。而 `SELECT` 沒有 `ORDER BY`，**留下哪一筆其實是不確定的**——同一句話在不同時候可能命中不同的人。

### 🔴 修復過程中發現：維度 A（@提及偵測）從來沒有運作過

原本以為「同名就跳過不猜」是安全的降級，因為還有 @提及可以精準找人。查證後發現**並非如此**。

`discord.py` 的 `clean_content`（`message.py:2556-2576`）會把 `<@123>` 轉寫成 `@顯示名稱`：

```python
def resolve_member(id: int) -> str:
    m = self.guild.get_member(id) or utils.get(self.mentions, id=id)
    return f'@{m.display_name}' if m else '@deleted-user'
```

而全專案 8 處內容來源**全部**使用 `clean_content`，維度 A 的正則卻是 `re.findall(r'<@!?(\d+)>', content)`——它要找的原始標記在存進資料庫前就已被替換掉。`message.mentions` 這個權威來源則從未被使用。

**結論：名稱比對不是備援，它是先前唯一能運作的人物識別機制。** 因此必須先修好維度 A，「同名跳過」的降級才是安全的。

### 修復內容（三步，順序不可顛倒）

| 步驟 | 內容 |
| :--- | :--- |
| **1. 修好維度 A** | 呼叫端從 `discord.Message.mentions` 取權威 `user_id` 與 `display_name`，以 `explicit_mentions` 參數傳入；原正則保留為 fallback（處理 Slash 指令參數中使用者自行打出的原始標記）|
| **2. 同名整組排除** | `get_known_users_map()` 先建 `name → set(user_ids)`，對應多人的暱稱整組排除而非任選；行為由「不確定」變為「確定性」：要嘛找對人，要嘛找不到，不會找錯人。碰撞名單變動時輸出一次 warning |
| **3. 補上被提及者的權威名稱** | `explicit_mentions` 夾帶的 `display_name` 填入 `names`，堵住「首次被提及而尚無畫像者，建檔名稱退回模型輸出」的缺口（P0-1 修復留下的殘餘漏洞）|

三處呼叫端皆已接上 `mentions`：對話頻道（`client.py:385`）、監聽頻道（`client.py:146`）、回覆端畫像檢索（`client.py:208`）。`/kurisu-search` 不傳（Slash 參數無 Discord 提及物件），由正則 fallback 處理。

### 副作用

@提及從此真正生效，被提及者的畫像會開始正常進入 prompt——這是原始設計意圖，但先前從未實現過。

## 🟡 P2-2：`remove_facts` 過濾範圍過廣 ✅ 已修復

**位置**：`memory_manager.py` 的 `merge_facts` 剔除段落

同樣是雙向子字串比對，籠統的 remove 詞會誤刪無關事實：

```
remove_facts=['台中'] 套用到
  ['以前在台中唸書' (hits=5), '住在台中市' (hits=2)]
→ 兩條全被刪除，只剩新增的 ['搬到台北了']
```

「以前在台中唸書」其實仍然成立，卻連帶被清掉。

### 修復內容

新增 `should_remove_fact(fact, term)`，把三種情況分開判定：

| 情況 | 判定 |
| :--- | :--- |
| 完全相同 | 刪除 |
| 刪除詞**包含**整條事實 | 刪除（模型引述得比事實更完整，識別明確）|
| 事實**包含**刪除詞 | 需達最低引述比例：`len(term) >= max(2, ceil(0.4 × len(fact)))` |

**不能改成「只接受完整引述」**：`prompts.py` 的範例本身就教模型給部分引述（事實「住在台中市」對應 `remove_facts: ["住在台中"]`），改嚴會讓正常更正失效。

### 實測結果

```
既有: [('以前在台中唸書', 5), ('住在台中市', 2), ('喜歡台中的太陽餅', 8)]
remove=['台中'] -> [('以前在台中唸書', 5), ('喜歡台中的太陽餅', 8), ('搬到台北了', 1)]
```

「住在台中市」仍被正確刪除，另外兩條保留。這個區辨是比例門檻自然產生的：`台中` 佔「住在台中市」(5 字) 的 40%，卻只佔「喜歡台中的太陽餅」(8 字) 的 25%——與更正主題相關的事實較短、佔比高，離題的事實較長、佔比低。

### 刻意保守的取捨

刪除是**不可逆**操作，因此門檻偏向保留。代價是：籠統的刪除詞若被擋下，過時事實會繼續留著（例如 `remove=['咖啡']` 無法刪除「每天早上都要喝一杯咖啡」）。

這是有意識的選擇——過時事實是**可見的**，模型日後可再以更完整的引述更正；誤刪一條仍然成立的事實則**無法復原**。被擋下的刪除詞會寫入 debug log，便於追查「為什麼這次更正沒生效」。

門檻值定義於 `memory_manager.py` 的 `FACT_REMOVAL_MIN_RATIO` / `FACT_REMOVAL_MIN_LENGTH`。

## 🟡 P2-3：維度 C「最近在場者」不篩相關性

只要在最近 15 則訊息裡講過話就被當「在場關係人」拉進 context，與當前話題是否相關完全不論。忙碌頻道中會把無關者的人設與**態度指令（Tier）**一併塞進 prompt。

## 🟡 P2-4：A/B/C 三維度先到先得就截斷 ✅ 已解決（P2-1 的副產品）

原本 `target_other_uids[:max_others]` 無相關性排序，維度 C 硬湊進來的「碰巧講過話」的人
可能佔掉本該給 @提及對象的配額。

修 P2-1 時為 `resolve_mentioned_user_ids()` 加上回傳優先序（@提及 → 較長暱稱 → 較短暱稱），
維度 C 才接在其後，因此截斷時 @提及必定優先保留，原描述的情境已不會發生。

## 🟡 P2-5：監聽佇列無數量上限，純防抖可能長時間不觸發 ✅ 已修復

**位置**：`ai/memory_extractor.py` 的 `add_listen_message`

每來一則訊息就 `cancel()` 舊計時器再重排 4 秒。熱絡頻道若持續有人發言（間隔都 <4 秒），計時器被無限重置，佇列**沒有任何數量上限**地成長，直到出現一次 4 秒空檔才一口氣送出 → 單次超大 prompt。

`memory_sys_design.md` §4 宣稱觸發條件是「每累積滿 15 則**或**靜默 10 分鐘」，實作只有 4 秒防抖、沒有則數門檻——少掉的正是防止佇列爆掉的保險。

### 修復內容

`add_listen_message()` 補上則數上限，兩種觸發條件滿足其一即提煉：

- 靜默滿 `listen_debounce_seconds`（每來一則新訊息重設計時）
- 佇列累積滿 `listen_max_queue_messages`（預設 15）立即觸發

滿載時會先取消尚在等待的防抖任務、取出整批，再以背景任務提煉（避免長時間佔住佇列鎖）。上限以**頻道為單位**計算。

這道保險同時解除了對 `listen_debounce_seconds` 的調整限制——先前不敢調大是因為會放大佇列爆掉的風險，現在有則數上限兜底。調大防抖是提升監聽頻道歸屬品質最有效的旋鈕（讓模型一次看到更完整的多輪脈絡），若要調整建議一併確認則數上限是否合適。

## 🟡 P2-6：監聽佇列在記憶體，重啟即遺失 ✅ 已解決（背景撿漏的副產品）

`self._listen_queue` 仍是 in-memory dict，bot 重啟時佇列內容確實會消失。但這已不再造成
品質退化：那些訊息在 DB 中仍是 `extracted=0`，`sweep_unextracted()` 會在一個掃描週期內
撈回、依頻道分組，並交給**正確的多人對話引擎**處理。

原描述的「退化成 JIT 單人視角」已不存在——JIT 機制本身已隨 P0-3 一併廢除。

## ❓ 監聽頻道的好感度語意 ✅ 已調整

批次 prompt 要求對參與者評估 `favorability_delta`，措辭為「-1 ~ -2：惡意挑釁、無理辱罵」，**沒有限定「對紅莉栖」**。因此兩位群友在監聽頻道互嗆，可能讓其中一方對紅莉栖的好感度被扣分——而 bot 根本沒參與那場對話。

單人引擎的 prompt 措辭則明確以紅莉栖為中心（「送紅莉栖禮物、關心紅莉栖」）。此不一致是否為刻意設計，需產品判斷。

## 🆕 別名系統（Alias）— 已實作

**動機**：Discord 顯示名稱往往不是群友實際互稱的稱呼。若 A 用綽號叫 B，而系統只認得
display_name，B 就完全無法被識別——這是 P1-2 修復後浮現的真實缺口（同名者被排除比對後，
更需要一個能用的替代稱呼）。

### 設計

別名存於 `user_profiles.aliases`，**與 `user_name` 分開**：`user_name` 由 Discord 權威覆寫
（手動改會被還原），`aliases` 不受提煉碰觸，設了就保留。因此它同時是「緊急人工修正」的可行管道。

別名納入 `get_known_users_map()`，因此**同時作用於讀（畫像檢索）與寫（提煉白名單）**，
沿用完全相同的碰撞規則與 `is_matchable_name()` 過濾。

### 自動學習的五道校驗

提煉可提議別名（prompt 新增第 5 條規則與 `aliases` 輸出欄位），但須全部通過才生效：

1. 通過 `is_matchable_name()`（非停用詞、長度足夠、非過短英數）
2. 不與任何既有的 user_name 或別名碰撞 — **這道擋掉冒名**
3. 歸屬對象必須在本次 `allowed_uids` 內 — 沿用既有白名單
4. 未超過 `max_aliases_per_user`（達上限拒絕新增，不自動淘汰）
5. 記錄來源：誰的哪則訊息、哪個頻道、何時 — 可稽核、可撤銷

第 5 點是讓自動學習可被接受的關鍵：事實寫錯是靜默的，**別名寫錯會立刻表現為
「機器人把 X 當成 Y」**，只要有來源記錄就查得到、也撤得掉。

### 由條件 3 導出的邊界（刻意保留）

`allowed_uids` 由「發言者 + 已識別的提及對象」組成，因此**別名只能在當事人於該次對話中
在場時學到**。一個從未現身的人，系統不會替他建立稱呼。

這不是缺陷而是安全性質：要讓「A 提到從不發言的 C 的綽號」也能成立，就得讓模型猜
「這個沒見過的綽號是誰」——正是整份文件一路在移除的那種猜測。學到之後即永久有效，
包含當事人日後缺席的場合，因此機制會從「在場」自然 bootstrap。

### 別名必須寫進 prompt（實作中補上的缺口）

初版只讓別名參與「解析出該載入誰的畫像」，卻沒把對應關係寫進 prompt。模型看到的是
`【daru_1024】(ID: 2002)` 配上對話中的「桶子」，只能盲猜兩者是同一人——在場人數一多就
不可靠，猜錯時事實會被歸給發言者或整個漏掉。

現以 `format_alias_hint()` 在**五個把人放進 prompt 的渲染點**全部附上別名
（提煉端單人／多人引擎、回覆端發言者／其他群友）：

```
- 【daru_1024】（大家也叫他：桶子）(ID: 2002)
```

> **分工再確認**：系統負責「對的人在候選名單裡」「對應關係可見」「寫入受白名單限制」；
> **「這句話在講誰」始終是模型的語意判斷**。別名讓判斷有據可依，但沒有把判斷本身變成
> 確定性的——一句話含多個綽號或使用代名詞時，模型仍可能歸錯。

### 指令

`/kurisu-alias`（add／remove／list）。呼叫者身分取自 `interaction.user`，不信任訊息內容，
因此無法透過聊天內容偽造。代他人操作需 `manage_guild` 權限。`list` 會顯示每個別名的
來源、時間與提出者，供稽核。

## 🟠 P4-1：`interaction_notes` 完全覆寫，無任何保護

**位置**：`ai/memory_extractor.py` 的 `_safe_apply_updates`

```python
merged_notes = str(notes).strip() if (notes and str(notes).strip()) else cur_notes
```

模型每次提煉都**整份取代**互動印象，只有在回傳空字串時才保留舊值。

這與 `memory_sys_design.md` §7 的核心哲學直接矛盾——那套「絕不洗白」的保護只涵蓋 `facts`，不涵蓋 `interaction_notes`：

| 記憶類型 | 保護 |
| :--- | :--- |
| `facts` | 增量聯集 + `hits` 熱度 + 否定推翻 + 刪除門檻（四層）|
| `interaction_notes` | **無** |

互動印象承載的是【核心性格】這種累積最久、最難重建的內容，一次壞的提煉就永久消失。

**緩解因素**：prompt 有明確要求「參考歷史已有記錄請參考保留並適度微調深化」，且模型在 prompt 中看得到目前的印象，正常情況會演進而非清空。因此這是**潛在的單點失效**而非持續發生的問題。

**可能的修法**：比照事實的做法保留舊值直到新值明顯更完整（例如長度門檻），或把三個維度（核心性格／社交關係／近期動態）拆開分別合併——【核心性格】應該穩定，【近期動態】本來就該滾動更新。

## 🟡 P4-2：好感度扣分無跨日累積限制

**位置**：`memory_manager.py` 的 `calculate_favorability_update`

```python
if delta > 0:
    available_gain = max(0, gain_limit - daily_gain)   # 有累積追蹤
    actual_delta = min(delta, available_gain)
elif delta < 0:
    actual_delta = max(delta, -loss_limit)             # 只有單次夾限
```

加分受 `daily_favorability_gain` 追蹤並以 15 分/日為上限；扣分只有「單次夾限 `daily_loss_limit`（100）」，而模型的 delta 範圍是 -2 ~ +2，**等於完全沒有限制**。

後果是不對稱的：連續幾次誤判可以讓關係階級從 `cherished` 快速掉到 `stranger`，而回升受每日 15 分上限約束，要好幾天。

此項與 [`doc/improv.md`](improv.md) 6.1 記錄的「每日增減上限明顯不對稱」是同一件事，當時判斷需與產品邏輯確認是否為刻意設計。

**位置**：`filter_facts_three_tracks` + `extract_keywords`

中文靠 2/3-gram 滑動窗口比對重疊字數，語意相反或無關但字面相似的舊事實會一起被選中塞進 prompt，稀釋當前話題焦點——「文不對題」最直接的來源。

## 提煉路徑總覽

系統有 **2 種提煉引擎**（決定模型看到什麼）與 **4 條觸發路徑**：

| 引擎 | Prompt | 視角 |
| :--- | :--- | :--- |
| `extract_and_update()` | `build_multi_entity_extraction_prompt` | **單人主角**——有明確發言者，其他人只是配角畫像 |
| `_process_batch_extraction()` | `build_batch_dialogue_extraction_prompt` | **多人對話**——整段多輪對話，參與者平等分析 |

| 路徑 | 觸發時機 | 引擎選對？ | 標記 `extracted`？ | 缺陷 |
| :--- | :--- | :--- | :--- | :--- |
| **收尾提煉** | 回覆後（單人） | ✅ | ❌ **沒標記** | P0-3 |
| **JIT** | 回覆**前**，每位在場者 | ❌ **用錯**（單人視角處理多人對話） | ✅ | P0-1、P0-3 |
| **監聽批次** | 監聽頻道靜默 4 秒 | ✅ | ✅ | P1-3、P2-5、P2-6 |
| **Burst 批次** | 回覆後（多人） | — | — | P0-2 **函式不存在** |

> **JIT 的本質**：它不是一種提煉「方法」，而是一種**觸發策略**——沒有自己的 prompt，只是「從 DB 撈積壓訊息 → 丟給單人引擎 → 標記已處理」。它的病灶是**用錯引擎**，而非「少傳 `other_users` 參數」：積壓的監聽訊息本來就是多人對話，卻被拆成一個人的獨白來分析。
>
> 也因此，「把當前頻道的 `other_users` 補傳給 JIT」是錯誤的修法——那些積壓的話是在**別的頻道、跟別人**講的，用現在在場的人去解讀反而更容易歸屬錯人。

## 四個根因

所有症狀收斂到四個根因，修復應以根因為單位而非逐一補洞：

| 根因 | 說明 | 對應症狀 |
| :--- | :--- | :--- |
| **RC1** 觸發與引擎的對應關係錯亂 | 沒有統一的調度層決定「哪些訊息、用哪個引擎、誰負責標記」 | P0-2、P0-3、JIT 用錯引擎 |
| **RC2** `extracted` 旗標責任不一致 | 三條路徑中兩條標記、一條不標記 | P0-3、收尾提煉重複被撈 |
| **RC3** `allowed_uids` 建法不一致 | 回覆路徑含 @提及／名稱掃描，監聽路徑只含發言者 | P1-3 |
| **RC4** `user_name` 由 LLM 路徑寫入 | 名字是 Discord 權威資料，不該由模型推斷或回填 | P0-1、加劇 P1-2 |

## 修復優先順序

| 優先 | 項目 | 理由 |
| :--- | :--- | :--- |
| **P0** | P0-1、P0-2、P0-3（**必須一起處理**，同屬 RC1/RC2/RC4） | 唯一會持續**污染資料**的一組；且彼此耦合，單獨修任一項會引入新問題 |
| **P0.5** | 修復正式機上已污染的 `user_name` 與灌水的 `hits` | 越晚做越髒；必須在寫入路徑修好**之後**做 |
| **P1** | P1-1 否定語意 | 有自我強化的正回饋，會越來越常講錯話 |
| **P1** | P1-3 監聽白名單（RC3） | 招牌功能實質失效 |
| **P1** | P1-2 暱稱碰撞 | 被 P0-1 主動製造；修完 P0 後仍會自然發生 |
| **P2** | P2-1 ~ P2-6 | 影響單次回覆品質或穩定性，但不累積污染 |
| **P3** | 語意 RAG | 需 embedding，建議獨立評估 |

**優先順序判準**：**資料污染優先於功能缺失**。功能沒跑只是少了記憶；資料錯了是往後每次回覆都帶著錯的前提，而且會越積越多。

---

## 為什麼 P0 三項必須一起修

- 只補 `process_burst_dialogue`（P0-2）→ Burst 訊息會被 JIT 和批次提煉**各處理一次**，加劇 P0-3。
- 只修名字傳參（P0-1）→ 模型回傳的 `user_name` 仍會被寫入（RC4 未解），污染只是變罕見而非消失。
- 只讓收尾提煉標記 `extracted`（P0-3 的一半）→ 仍有 JIT 搶先處理的競態，因為 JIT 在回覆**前**就啟動了。

三者共用同一個修復方向：**建立單一提煉調度路徑**，統一決定引擎、白名單與標記責任。

### 建議的目標架構

```
                    ┌──────────────────────────────────┐
   回覆送出後 ─────→│  統一提煉入口                    │
   監聽防抖到期 ───→│  1. 依發言者人數選引擎           │
                    │     (>=2 人 → 多人對話引擎)      │
                    │  2. 白名單 = 發言者 + @提及/名稱 │
                    │  3. 提煉並套用                   │
                    │  4. 統一 mark_messages_extracted │
                    └──────────────────────────────────┘
```

在此架構下 **JIT 可以整個廢除**：各路徑提煉完即標記，積壓只會來自失敗案例（JSON 解析錯誤、重啟遺失佇列），改由低頻背景掃描撿漏即可，不需要在每則訊息上觸發。
