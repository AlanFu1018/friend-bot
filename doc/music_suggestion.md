# 語音頻道感知與音樂推薦（Music Suggestion）

> 紅莉栖如何知道誰在語音頻道、如何結合在場者喜好推薦音樂，以及如何把推薦真的變成播放。
>
> 最後更新：2026-09-02，已對照程式碼核實。

---

## 1. 為什麼現在能「真的播放」

早期評估認為 Slash 指令走的是 Interactions API，interaction 只能由 **Discord 客戶端（真人）** 發起，bot 叫不動另一個 bot 的 Slash 指令；文字前綴指令也不可靠，因為多數音樂 bot 只剩 Slash 介面，且**通常會過濾掉其他 bot 送的訊息**。

現在群組換上的音樂 bot（Muse）解除了這兩個限制：

- 完全用 `m.`-prefixed 文字指令（見 [`doc/music_commands.md`](./music_commands.md)），不是 Slash 指令。
- **不會過濾 bot 訊息**——「只有自己發的訊息會被忽略」，其他 bot（含 friend-bot）發的 `m.play ...` 一樣會被讀取執行。

因此 friend-bot 只要把 `m.play <query>` 當成一則普通文字訊息發到頻道，Muse 就會真的執行。原本評估過並排除的做法（user token 模擬真人操作、friend-bot 自己接語音播放）依然不採用——前者違反 Discord ToS，後者需要 FFmpeg／yt-dlp 等大量額外依賴，現在也沒有必要了。

**最終設計**：紅莉栖依對話與在場者喜好判斷要不要點播，決定要播時在回覆末尾標記 `[play: 歌名 - 演出者]`，系統解析出查詢字串後，**在聊天訊息都送出後，另外發一則獨立的 `m.play` 指令訊息**（見第 4、5 節）。

## 2. 誰算「在場」

只認**發言人自己所在的語音頻道**。發言人不在任何語音頻道時，**完全不注入語音資訊**。

不去猜「人數最多的語音頻道」，理由有二：

1. 推薦對象的定義沒有歧義——發言人與同頻道的其他人必然重疊。若允許發言人不在語音也觸發，就會出現「聽眾是語音裡的人、但發問的是頻道外另一個人」的張力。
2. 多個語音頻道同時有人時只能靠人數猜，與專案一貫的**「寧可找不到也不猜」**原則相違。

代價是「在文字頻道幫語音裡的人點歌」這種情境不會觸發，這是刻意接受的取捨。

### 成員來源必須用 `voice_states`

`_resolve_voice_context()`（`bot/client.py`）用的是 `channel.voice_states` 而非 `channel.members`。

discord.py 的 `VoiceChannel.members` 實作是：

```python
for user_id, state in self.guild._voice_states.items():
    member = self.guild.get_member(user_id)
    if member is not None:        # ← 快取沒有就靜默跳過，不報錯
        ret.append(member)
```

`members` 是**特權 intent 且目前關閉**，因此 bot 重啟後若有人已在語音頻道中，`members` 可能回傳空清單——而且不會有任何錯誤訊號。

`voice_states` 回傳 `Dict[user_id, VoiceState]`，直接來自語音狀態快取、不依賴成員快取，因此可靠。

> `voice_states` intent 已內含於 `Intents.default()`，**不需修改 `main.py`，也不需在 Developer Portal 開啟任何東西**。

### 名稱解析兩段式

1. `guild.get_member(uid)` 有快取 → 用 `display_name`（Discord 權威且即時）
2. 沒有 → 退回 `user_profiles.user_name`（我們自己的畫像記錄）

第二段讓「成員快取不完整」不至於變成「不知道那是誰」——記憶系統剛好補上了這個洞。

## 3. 維度 D：語音在場者（唯讀）

語音在場者被加入 `resolve_multi_user_profiles()` 的人物識別，成為第四個來源：

| 優先序 | 來源 | 讀 | 寫 |
| :--- | :--- | :---: | :---: |
| 1 | A：@提及 | ✅ | ✅ |
| 2 | B：名稱／別名 | ✅ | ✅ |
| 3 | **D：語音在場者** | ✅ | ❌ |
| 4 | C：近期文字發言者 | ✅ | ❌ |

D 排在 C 之前，是因為「此刻和發言人同在一個語音頻道」比「15 則訊息前在文字頻道講過話」更能代表在場。

### 唯讀是結構保證，不是額外檢查

提煉端的白名單走的是 `resolve_mentioned_user_ids()`（**只含 A+B**），與畫像檢索的 `resolve_multi_user_profiles()` 刻意是**不同函式**。因此維度 D 不可能讓事實被寫到語音在場者身上。

> ⚠️ 若日後有人想把兩者「統一」成同一個函式，會讓維度 C 與 D 取得寫入權限，使誤判從「一次回覆變差」升級為「永久記錯人」。`test_voice_presence_never_grants_write_access` 專門守著這點。

## 4. 觸發判斷交給模型，代發交給標籤解析

Python 端**不做**「這是不是音樂話題」的關鍵字判斷，也不做「這句歌名聽起來對不對」的驗證。作法是：

- 發言人在語音頻道時，一律注入一小塊【語音頻道現況】
- 系統指令第 10 條說明何時該推薦、要不要點播、點播時該怎麼標記
- 模型若決定點播，會在回覆最後一行輸出 `[play: 歌名 - 演出者]`；`parse_music_play_tag()`（`ai/prompts.py`）把這個標籤從聊天文字中挖出來，回傳「乾淨的聊天文字」與「查詢字串」兩者
- `client.py` 的 `_handle_buffered_chat()` 先把乾淨的聊天文字正常送出（含多氣泡切分），**全部送完後**才呼叫 `_dispatch_music_command()` 另外發一則 `m.play <query>` 指令訊息

這符合專案的核心原則——**系統縮小範圍（誰在場、有哪些喜好），模型做語意判斷（現在該不該推薦、推薦什麼）**；而「標籤 → 動作」是本專案既有的模式（`[emotion:xxx]` 也是同一套 tag & strip 手法，見 `core/emotion.py`）。

### 為什麼聊天訊息與指令要分兩則發

- `m.play` 指令訊息本身沒有任何人格對話內容，混在聊天氣泡裡會很突兀，也會被記錄進對話歷史裡污染日後的 prompt。
- 分開發也讓「代發指令頻道」可以與「聊天頻道」不同（見下方 `command_channel_id`）——例如聊天在一般文字頻道，但指令固定送去 Muse 專用的頻道。
- Muse 不忽略 bot 訊息，但 friend-bot 自己的 `on_message` 一律忽略 `author.bot`，所以這則代發的指令訊息不會被 friend-bot 自己當成新訊息處理，不會有遞迴風險。

### Prompt 區塊

插在【其他群友畫像】之後、行事曆之前：

```
【語音頻道現況】:
- 頻道「一般」目前有 3 人：岡部、daru_1024（大家也叫他：桶子）、真由理
```

### 系統指令規則

```
10. 【音樂推薦與代發指令】：
   - 上下文若出現【語音頻道現況】，代表那些人此刻正和發言者同在語音頻道裡。
   - 當對話自然聊到音樂、心情或氣氛時，你可以推薦一首歌，並結合在場者已知的喜好挑選。
   - 你自己聽不到播放結果，但可以實際幫忙點播：決定要播放時，在回覆的最後一行加上
     `[play: 歌名 - 演出者]` 標籤。
   - 這個標籤不會被群友看到，系統會自動把它轉成真正的點播指令另外送出，
     所以回覆本文用自然口語帶出推薦就好，不要自己在文字裡輸出 `m.play` 這種指令格式，
     也不要說「我沒辦法播放」這種話——你現在點得動。
   - 不要每次都推薦或點播；只在話題自然帶到、你也判斷適合時才做，避免洗頻。
```

「你現在點得動」這句是必要的——否則模型仍會沿用舊的自我認知，承諾建議群友自己複製，而不是真的用標籤觸發代發。

### 喜好從哪裡來

在場者的事實**不是全量帶入**，而是經 `filter_facts_three_tracks()` 以當下對話為 query 篩選。這產生一個好效果：**聊到音樂時，話題軌道自然會把音樂相關的事實浮上來**；聊別的時候帶進來的就是別的事實，不會硬塞音樂偏好。

## 5. 相關設定

```yaml
music:
  enable_music_suggestion: true   # 關閉後不注入語音區塊、也不加入第 10 條規則、也不解析 [play:] 標籤
  play_command: "m.play"          # 換音樂 bot 時只要改這裡（含子指令，例如 "m.play"）
  voice_members_max: 5            # 最多帶入幾位在場者
  command_channel_id: ""          # 代發指令的目標頻道 ID；留空則送到觸發這次回覆的頻道
```

`command_channel_id` 也可以用 `.env` 的 `MUSIC_COMMAND_CHANNEL_ID` 設定（優先權高於 config.yaml，做法與 `REPLY_CHANNEL_IDS`／`LISTEN_CHANNEL_IDS` 一致）。

`play_command` 依然是設定項而非寫死在程式碼裡——**換音樂 bot 時唯一要改的就是這個字串**（前提是新 bot 一樣接受「純文字查詢」當參數；見第 6 節「換音樂 bot 需人工確認指令格式」）。

## 6. 已知限制

### 不會主動開場

只在有人講話、且對話自然帶到音樂時才推薦。「有人進語音就主動推薦」需要 `on_voice_state_update` 事件處理，目前刻意不實作——那會讓 bot 在人頻繁進出時變得聒噪。

### 推薦品質取決於累積的喜好

如果在場者的畫像裡沒有任何音樂相關事實，模型只能依對話氣氛泛泛推薦。這會隨著記憶累積而改善。

### 無法確認歌曲是否真的存在，也無法確認指令真的執行成功

紅莉栖推薦的歌名由模型生成，可能是幻覺（不存在的歌、錯誤的演出者）。`_dispatch_music_command()` 只確認訊息**送出成功**（HTTP 層面），不會去讀 Muse 的回覆判斷歌是否真的找到、佇列是否成功——這是刻意的取捨，驗證需要額外解析 Muse 的回覆格式，且找不到歌本來就是使用者能直接在頻道看到、自行修正的低成本失敗。

### 換音樂 bot 需人工確認指令格式

`play_command` 只控制前綴＋子指令字串。若新的音樂 bot 的參數格式不是「純文字查詢（歌名 - 演出者 / URL）」，需一併調整系統指令第 10 條與 `MUSIC_SUGGESTION_RULE` 的措辭。

### 目前只代發 `m.play`

`music_commands.md` 裡 Muse 支援的其他指令（`m.skip`、`m.pause`、`m.queue`、`m.favorites` 等）刻意沒有做成模型可觸發的標籤——這些指令沒有像「推薦歌曲」一樣自然的對話觸發時機（例如「什麼情況該自動跳過」沒有明確語意信號），貿然開放容易變成模型亂點造成群友困擾。若之後有明確需求，可以比照 `[play:]` 的 tag & strip 模式個別評估新增。
