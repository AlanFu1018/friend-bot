# 語音頻道感知與音樂推薦（Music Suggestion）

> 紅莉栖如何知道誰在語音頻道、如何結合在場者喜好推薦音樂，以及為什麼只能「建議」而不能直接播放。
>
> 最後更新：2026-08-31，已對照程式碼核實。

---

## 1. 為什麼只能建議，不能直接播放

**Discord API 不允許一個 bot 呼叫另一個 bot 的 Slash 指令。**

Slash 指令走的是 Interactions API，而 interaction 只能由 **Discord 客戶端（真人）** 發起。API 沒有任何端點讓 bot 去「觸發」另一個應用的指令——`POST /interactions/{id}/{token}/callback` 是用來**回應**自己收到的 interaction，不是發起別人的。

因此 Rythm 那整份 `/play`、`/skip`、`/queue` 指令清單，friend-bot 一個都叫不動。

其他被評估後排除的做法：

| 做法 | 為何不採用 |
| :--- | :--- |
| 發送 `!play xxx` 文字指令 | 現代音樂 bot 幾乎只剩 Slash 指令；且多數 bot 會過濾其他 bot 的訊息（本專案 `client.py` 也是這樣寫的） |
| 用 user token 模擬真人點指令 | **直接違反 Discord ToS**，帳號會被停權 |
| friend-bot 自己加入語音播放 | 技術可行（voice + yt-dlp + FFmpeg），但需要 FFmpeg、新增大量依賴、且 yt-dlp 對 YouTube 的相容性需持續維護。已評估後選擇不做 |

**最終設計**：紅莉栖依對話與在場者喜好推薦歌曲，並附上可直接複製的指令，由群友自己執行。

---

## 2. 誰算「在場」

只認**發言人自己所在的語音頻道**。發言人不在任何語音頻道時，**完全不注入語音資訊**。

不去猜「人數最多的語音頻道」，理由有二：

1. 推薦對象的定義沒有歧義——發言人與同頻道的其他人必然重疊。若允許發言人不在語音也觸發，就會出現「聽眾是語音裡的人、但發問的是頻道外另一個人」的張力。
2. 多個語音頻道同時有人時只能靠人數猜，與專案一貫的**「寧可找不到也不猜」**原則相違。

代價是「在文字頻道幫語音裡的人點歌」這種情境不會觸發，這是刻意接受的取捨。

### 成員來源必須用 `voice_states`

`_resolve_voice_context()`（`bot/client.py`）用的是 `channel.voice_states` 而非 `channel.members`。

discord.py 的 `VoiceChannel.members` 實作是：

```python
for user_id, state in self.guild._voice_states.items():
    member = self.guild.get_member(user_id)
    if member is not None:        # ← 快取沒有就靜默跳過，不報錯
        ret.append(member)
```

`members` 是**特權 intent 且目前關閉**，因此 bot 重啟後若有人已在語音頻道中，`members` 可能回傳空清單——而且不會有任何錯誤訊號。

`voice_states` 回傳 `Dict[user_id, VoiceState]`，直接來自語音狀態快取、不依賴成員快取，因此可靠。

> `voice_states` intent 已內含於 `Intents.default()`，**不需修改 `main.py`，也不需在 Developer Portal 開啟任何東西**。

### 名稱解析兩段式

1. `guild.get_member(uid)` 有快取 → 用 `display_name`（Discord 權威且即時）
2. 沒有 → 退回 `user_profiles.user_name`（我們自己的畫像記錄）

第二段讓「成員快取不完整」不至於變成「不知道那是誰」——記憶系統剛好補上了這個洞。

## 3. 維度 D：語音在場者（唯讀）

語音在場者被加入 `resolve_multi_user_profiles()` 的人物識別，成為第四個來源：

| 優先序 | 來源 | 讀 | 寫 |
| :--- | :--- | :---: | :---: |
| 1 | A：@提及 | ✅ | ✅ |
| 2 | B：名稱／別名 | ✅ | ✅ |
| 3 | **D：語音在場者** | ✅ | ❌ |
| 4 | C：近期文字發言者 | ✅ | ❌ |

D 排在 C 之前，是因為「此刻和發言人同在一個語音頻道」比「15 則訊息前在文字頻道講過話」更能代表在場。

### 唯讀是結構保證，不是額外檢查

提煉端的白名單走的是 `resolve_mentioned_user_ids()`（**只含 A+B**），與畫像檢索的 `resolve_multi_user_profiles()` 刻意是**不同函式**。因此維度 D 不可能讓事實被寫到語音在場者身上。

> ⚠️ 若日後有人想把兩者「統一」成同一個函式，會讓維度 C 與 D 取得寫入權限，使誤判從「一次回覆變差」升級為「永久記錯人」。`test_voice_presence_never_grants_write_access` 專門守著這點。

## 4. 觸發判斷交給模型

Python 端**不做**「這是不是音樂話題」的關鍵字判斷。作法是：

- 發言人在語音頻道時，一律注入一小塊【語音頻道現況】
- 系統指令第 10 條說明何時該推薦、推薦時要做什麼

這符合專案的核心原則——**系統縮小範圍（誰在場、有哪些喜好），模型做語意判斷（現在該不該推薦、推薦什麼）**。

### Prompt 區塊

插在【其他群友畫像】之後、行事曆之前：

```
【語音頻道現況】:
- 頻道「一般」目前有 3 人：岡部、daru_1024（大家也叫他：桶子）、真由理
```

### 系統指令規則

```
10. 【音樂推薦】：
   - 上下文若出現【語音頻道現況】，代表那些人此刻正和發言者同在語音頻道裡。
   - 當對話自然聊到音樂、心情或氣氛時，你可以推薦一首歌，並結合在場者已知的喜好挑選。
   - 推薦時附上可直接複製執行的指令，格式為：`/play 歌名 - 演出者`
   - 你自己無法播放音樂，指令要由群友複製去執行——用自然的語氣帶出來，別像客服念稿。
   - 不要每次都推薦；只在話題自然帶到時才做。
```

「你自己無法播放音樂」這句是必要的——否則模型可能承諾「我幫你放」這種它做不到的事。

### 喜好從哪裡來

在場者的事實**不是全量帶入**，而是經 `filter_facts_three_tracks()` 以當下對話為 query 篩選。這產生一個好效果：**聊到音樂時，話題軌道自然會把音樂相關的事實浮上來**；聊別的時候帶進來的就是別的事實，不會硬塞音樂偏好。

## 5. 相關設定

```yaml
music:
  enable_music_suggestion: true   # 關閉後不注入語音區塊、也不加入第 10 條規則
  play_command: "/play"           # 換音樂 bot 時只要改這裡
  voice_members_max: 5            # 最多帶入幾位在場者
```

`play_command` 做成設定項是因為輸出的只是一段給人複製的文字——**換音樂 bot 時唯一要改的就是這個字串**，不需動程式碼。

## 6. 已知限制

### 不會主動開場

只在有人講話、且對話自然帶到音樂時才推薦。「有人進語音就主動推薦」需要 `on_voice_state_update` 事件處理，目前刻意不實作——那會讓 bot 在人頻繁進出時變得聒噪。

### 推薦品質取決於累積的喜好

如果在場者的畫像裡沒有任何音樂相關事實，模型只能依對話氣氛泛泛推薦。這會隨著記憶累積而改善。

### 無法確認歌曲是否真的存在

紅莉栖推薦的歌名由模型生成，可能是幻覺（不存在的歌、錯誤的演出者）。系統不會去驗證——指令執行後找不到歌，是使用者會直接看到的失敗，成本低且可自行修正。

### 換音樂 bot 需人工確認指令格式

`play_command` 只控制前綴。若新的音樂 bot 的參數格式不是「歌名 - 演出者」，需一併調整系統指令第 10 條的措辭。
